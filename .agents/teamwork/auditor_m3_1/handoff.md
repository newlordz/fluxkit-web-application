## 2. Forensic Observations

### 2.1 No Hardcoding / Dynamic Output Variance
An independent forensic test (`forensic-check.cjs`) was executed to challenge the hypothesis that tools might return fixed canned fixtures. Distinct dynamic inputs were supplied to all 8 tools:
1. `pdfToWord`: Input "UniqueAlpha12345" produced a DOCX package whose `word/document.xml` contained "UniqueAlpha12345", while input "UniqueBeta67890" produced "UniqueBeta67890" with differing byte lengths and hashes.
2. `pdfToPPT`: Input "SlideTitleAlpha" generated `ppt/slides/slide1.xml` with "SlideTitleAlpha"; "SlideTitleBeta" generated "SlideTitleBeta".
3. `pdfToExcel`: Tabular inputs `SKU123 | 100` and `ORD789 | 999` generated corresponding SpreadsheetML rows in `xl/worksheets/sheet1.xml`.
4. `wordToPDF`: Dynamic headings and paragraphs were rendered onto PDF canvas using font metrics and extracted back with exact string fidelity.
5. `pptToPDF`: Dynamic outlines rendered into landscape slide cards with matching titles and bullet counts.
6. `excelToPDF`: Distinct CSV datasets (`Laptop, $1200` vs `Alice, Engineering`) rendered into printable tables with normalized columns.
7. `pdfToJPG`: 1-page PDF produced authentic JFIF JPEG with SOI `0xFF,0xD8` and EOI `0xFF,0xD9`; 2-page PDF produced a multi-file PK-ZIP archive.
8. `jpgToPDF`: Single image yielded a 1-page PDF; two images yielded a 2-page PDF.

*Conclusion*: All 8 engines execute genuine dynamic parsing, formatting, and document generation.

### 2.3 OpenXML Standards & PK-ZIP Integrity
Inspected binary packages generated by `pdfToWord`, `pdfToPPT`, and `pdfToExcel`:
- Local file header magic bytes: `0x50 0x4B 0x03 0x04` (`0x04034b50` little-endian) confirmed at offset 0.
- Central directory header magic bytes: `0x50 0x4B 0x01 0x02` (`0x02014b50` little-endian) confirmed.
- End of Central Directory (EOCD) magic bytes: `0x50 0x4B 0x05 0x06` (`0x06054b50` little-endian) confirmed.
- CRC-32 calculation: `computeCRC32` implements standard polynomial `0xedb88320` and matches bitwise checksums of decompressed XML parts.
- Standard parts present: `[Content_Types].xml`, `_rels/.rels`, main document parts (`word/document.xml`, `ppt/presentation.xml`, `xl/workbook.xml`), and style/relationship parts.

### 2.4 Buffer Alignment & JpegEmbedder Safety
Investigated `toCleanUint8Array` in `src/services.ts` (lines 198–228):
- `pdf-lib`'s `JpegEmbedder` instantiates `new DataView(imageData.buffer)` without passing `byteOffset`. Sliced `Uint8Array`s or pooled Node `Buffer` instances with `byteOffset > 0` cause `dataView.getUint16(0)` to read the beginning of the underlying memory pool rather than the JPEG, crashing with `"SOI not found in JPEG"`.
- `toCleanUint8Array` tests if `u8.byteOffset === 0 && u8.buffer.byteLength === u8.byteLength`. If not, it allocates an isolated `new Uint8Array(u8.byteLength)` and copies data.
- Empirical test: A buffer with `byteOffset: 64` was passed into `toCleanUint8Array`; the returned buffer had `byteOffset === 0` and embedded into `pdf-lib` cleanly without error.

## 4. Caveats

1. **Text Extraction Scope in Scanned Documents**:
   - `extractPDFPages` parses PDF content streams (`Tj`, `TJ` operators). Pure raster scanned PDFs with zero text streams will yield empty text; OCR processing for raster-only documents is explicitly scoped for Milestone 4 (`#ocr`).
2. **Complex Office Elements**:
   - In-browser OpenXML generation creates standard document structures (headings, paragraphs, tables, slides, shapes). Proprietary binary macros (VBA) and 3D objects are not embedded, matching standard client-side office export patterns.
